## Year split policy (applies to every step)

Let the years be Y1 < Y2 < ... < Y8 (taken from the data, not assumed).

| Use | Years | Rule |
|---|---|---|
| Static training set (Steps 3-6) | Y1-Y4 (first half) | Fit scaler, any feature selection, and models here only |
| Validation (model selection) | Inside Y1-Y4 only, using forward chaining (train on Y1..Yk, validate on Yk+1) | Never touches Y5-Y8 |
| Held-out test set (Steps 5-6) | Y5-Y8 | Used for final scoring only; report per year |
| Sustainable-approach experiments (Step 7) | Rolling: for each test year Yt, training data is limited to years before Yt | Test year is never in training |

The first-half/second-half split is the default. The reviewer should challenge it; if the data shows a better cut (for example a sharp drift point found in Step 2), the revised plan may change it. **That choice must be justified from training-year information or fixed before looking at test results**, not tuned on test results.

Leakage rules:
1. Scaler, feature selection, thresholds, and hyperparameters are fit on training years only.
2. Step 2 drift statistics use all years, but they are descriptive. They must not be used to select features, tune models, or choose the split cut with test-year labels or test-year features. Drift between training years is fine to use.
3. No shuffled random train/test split across years anywhere. A random split inside one year is only allowed as a labeled sanity baseline (and is reported as such, not as the main result).
4. Duplicate apps: check for identical rows across years in Step 1. If the same feature vector appears in train and test years, report it and decide with the reviewer whether to drop it.

## Step 1: Prepare the data

Approach
1. Inspect `input_data/`; update AGENTS.md dataset section (file names, year, label encoding, value types).
2. `load_file(path)`: read one file, drop the first column, return features. Check the shape is (1500, 1848) after the drop and fail loudly otherwise.
3. `parse_filename(path)`: return `(year, label)` using a strict regex. Raise an error on any file that does not match, and never guess. Encode malware = 1, goodware = 0.
4. `build_dataset(input_dir)`: concatenate everything into one DataFrame with the 1,848 feature columns plus `label` and `year`. Combine files per year, then across years. Column names must be identical across files (assert it).
5. Data-quality checks: missing values, non-numeric values, constant columns, duplicate rows within and across years, malware share per year.

Files created
- `src/config.py`, `src/data_loading.py`, `src/main.py` (data step), `results/step1_counts_per_year.csv`
- `docs/step1_data_summary.md`: files loaded per year, rows/columns after dropping, malware/goodware counts per year, any quality issues.

How it is tested (tester writes `tests/test_step1_*.py` from the assignment and this plan)
- The first column is dropped (shape is 1,848 features; the first-column values are not in the result).
- Labels match the file name for every file; an unknown name raises an error.
- Every year has the expected row count (files per year x 1,500) and the columns are identical across years.
- No missing labels or years; counts per year in the report match the code output.
- `tests/step1_test_log.md` holds the output.

## Step 2: Handle data drift

Approach
1. Per-feature drift between years: for each feature compare its distribution in each year with the first year (and year-to-year). Because API-call features are probably binary or sparse, use measures that suit that:
   - Two-sample Kolmogorov-Smirnov test (the assignment's suggestion), with Benjamini-Hochberg correction across the 1,848 features. Note: for binary features KS reduces to a difference in proportions, and I will say so in the report.
   - Change in feature prevalence (share of apps using the API call), which is easier to read.
   - Optionally, Jensen-Shannon distance on binned values if features are counts.
2. Year-by-year drift summary: number of significant features and mean KS statistic for every pair of years, shown as an 8x8 heatmap; identify which years differ the most.
3. Top drifting features per year pair.
4. Concept drift check: the same measures separately for malware and goodware, and a "year classifier" check (how well a simple model can tell year A from year B using the features).
5. Run the analysis separately for each class, so a change in class mix over years is not read as feature drift.

Files created
- `src/drift.py`, `results/step2_ks_matrix.csv`, `results/step2_top_features.csv`, `results/step2_drift_heatmap.png`
- `docs/step2_drift_analysis.md`: how drift was measured, features that drift most, years that differ most, and the effect on the split choice (Step 3).

How it is tested
- Synthetic data with known drift: identical distributions give a KS statistic near 0 and few significant features; a shifted feature is detected.
- The result matrix is symmetric with a zero diagonal; the number of features is 1,848; p-values lie in [0, 1].
- No modification of the input dataframe (the function does not change data in place).
- `tests/step2_test_log.md`.

## Step 3: Preprocess data for model training

Approach
1. Split by year per the policy above: train = Y1-Y4, test = Y5-Y8. Return train and test as separate objects and keep the `year` column so later steps can report per year.
2. Remove the `label` and `year` columns from the feature matrix before scaling.
3. Scaling: `StandardScaler` (fit on train only, then transform train and test). If Step 1 shows the features are binary, the reviewer and I will decide whether scaling is useful or whether `MaxAbsScaler`/no scaling suits sparse data better; the choice and the reason go into the report. Fit the scaler inside a scikit-learn `Pipeline` so that any cross-validation also refits it per fold.
4. Drop constant columns using training data only (the same columns are dropped from test).
5. Save the fitted scaler and the list of kept features in `outputs/`.

Files created
- `src/preprocessing.py`, `results/step3_split_summary.csv` (rows and class balance per year and per split)
- `docs/step3_preprocessing.md`: scaling method, train/test years, how leakage is prevented.

How it is tested
- No year appears in both train and test; every test year is later than every training year.
- Scaler statistics (mean, scale) equal the training-set mean and standard deviation, not the whole dataset's. Changing the test data must not change the scaler.
- Train and test have the same feature columns in the same order; no `label` or `year` column in X.
- Row counts add up to the Step 1 total.
- `tests/step3_test_log.md`.

## Step 4: Apply machine learning classifiers

Approach
1. Models (scikit-learn): Logistic Regression (linear, fast, interpretable baseline), Random Forest (non-linear, robust to unscaled features, gives feature importance), and Linear SVM or Gradient Boosting as an optional third. Add `DummyClassifier(strategy="most_frequent")` as a floor baseline.
2. Hyperparameters: a small grid per model, chosen with forward-chaining validation inside Y1-Y4 (not random k-fold, which would mix years). Fix `random_state=42`. Use `class_weight="balanced"` only if Step 1 shows a large imbalance.
3. Train each model on the training set; save the fitted model and its parameters.

Files created
- `src/models.py`, `outputs/models/*.joblib` (not committed), `results/step4_best_params.csv`
- `docs/step4_models.md`: classifiers, why chosen, hyperparameters, and how they were selected.

How it is tested
- Each model is a scikit-learn estimator that is fitted and can predict with the right output shape.
- Training uses only rows from the training years (check the training index against the years).
- Results are reproducible: two runs with `random_state=42` give identical predictions.
- Hyperparameter search folds respect time order (train years < validation year).
- `tests/step4_test_log.md`.

3. Output one comparison table: rows = classifiers, columns = metrics. Also report the same metrics on the training set to show the size of the generalization gap (clearly labeled).

## Step 7: Sustainable ML approach

Approach: compare strategies on the same rolling test years (Y5-Y8), with the "never updated" model from Step 4 as the reference.

| Strategy | Description |
|---|---|
| A. Static (never updated) | Step 4 model trained on Y1-Y4, used for all test years |
| B. Periodic retraining, expanding window | Before testing year Yt, retrain on all years before Yt |
| C. Periodic retraining, sliding window | Retrain on the most recent W years before Yt (for example W = 2 or 3) |
| D. Incremental learning | `SGDClassifier` (log loss) or another model with `partial_fit`; update with each new year's labeled data after it is tested |

Rules and questions
- Always test on year Yt using only data from years before Yt (a "test-then-train" or prequential order). The scaler is refit (or updated with `partial_fit` of `StandardScaler`) from the same past data only.
- Label delay: assume the labels for year Yt become available only after year Yt, so the model for Yt+1 can use Yt. State this assumption in the report.
- Cost: record the training time and data size of each strategy so the report can discuss the accuracy vs. retraining cost trade-off.
- Optional, if time allows: retrain only when a drift or performance alarm fires (for example when the number of drifted features from Step 2 passes a threshold), compared with retraining every year.
- Window length W is chosen using only years up to Y4 or fixed in advance, not tuned on the test years. If W is explored, the tuning results are shown for all values (no cherry-picking).

Files created
- `src/sustainable.py`, `results/step7_strategy_comparison.csv`, `results/step7_strategy_by_year.png`
- `docs/step7_sustainable_approach.md`: approaches tried, comparison with the never-updated model, conclusions for the one-page report.

How it is tested
- For every strategy and test year, the training years are all strictly earlier than the test year (checked by recording the training years used).
- Strategy A reproduces the Step 5/6 numbers exactly.
- The sliding window uses exactly W years; the expanding window uses all earlier years.
- `partial_fit` runs on a year-by-year stream give the declared number of updates; results are reproducible with `random_state=42`.
- `tests/step7_test_log.md`.

## Review and test workflow (every step)

Roles and what each is allowed to see (from the assignment):
- Builder: writes all code in `src/` and the report in `docs/`. Reads AGENTS.md and PLAN.md.
- Reviewer (fresh session): sees only AGENTS.md, PLAN.md, and the git diff of the step. Writes `reviews/stepN_review.md` covering bugs, leakage between years, wrong metrics, unclear code, mismatch with PLAN.md. Step 0 is different: the reviewer sees the assignment, AGENTS.md, and PLAN.md only, and writes `reviews/step0_plan_review.md`.
- Tester (fresh session): sees the assignment, AGENTS.md, and PLAN.md, but not the builder's explanations or reports. Writes `tests/test_stepN_*.py`, runs them with `python harness.py test N`, and saves output to `tests/stepN_test_log.md`.
- Student (lead engineer): reads each review, writes the decision log (accepted/rejected with a reason for every comment) at the end of the review file, and the decisions on failed tests in the test log. Verifies at least two results independently (for example rerun the Step 1 counts and recompute one accuracy by hand) and records how.

Cycle per step: build -> commit `[builder]` -> review -> commit `[reviewer]` -> tests -> commit `[tester]` -> student decisions -> builder fixes accepted items -> rerun tests -> commit `[builder]` -> commit `[student]` for decision logs. Transcripts are saved by the harness after each session.
